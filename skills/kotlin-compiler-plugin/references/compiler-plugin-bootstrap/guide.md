# Bootstrapping a Kotlin Compiler Plugin

This skill produces a working **multi-module Gradle project** containing a Kotlin compiler plugin and a sample module that consumes it. The plugin loads, runs during compilation, and can observe or transform IR.

A related working example lives at `skills/compiler-plugin-bootstrap/example/` (`hello-plugin`), pinned to Kotlin 2.3.21. It demonstrates the same module layout and `META-INF/services` wiring but uses simpler `println` / file I/O for plugin-side logging instead of the `MessageCollector` pattern shown in this skill — treat it as a structural reference, not as a verbatim companion to the text below. The instructions below are self-contained.

## Conceptual primer

A Kotlin compiler plugin is a JAR loaded by `kotlinc` via the `-Xplugin=` flag. It registers **extensions** that hook into compilation phases:

| Phase | Extension type | Skill |
|---|---|---|
| **Frontend** (parse + type-check, called K2 / FIR) | `Fir*Extension` | see `fir-*` skills |
| **Backend** (IR → bytecode, called IR / Intermediate Representation) | `IrGenerationExtension` | see `ir-*` skills |

The compiler discovers your plugin through `META-INF/services` (Java's ServiceLoader: the JVM looks in `META-INF/services/<interface-FQN>` for implementations) and instantiates your `CompilerPluginRegistrar`. This skill covers the JVM target only — Kotlin/JS, Kotlin/Native, and multiplatform plugins need additional wiring not described here.

## Required project layout

```
my-plugin/
├── settings.gradle.kts
├── gradle.properties
├── build.gradle.kts
├── gradlew                        ← generated by `gradle wrapper`
├── gradle/wrapper/                ← generated by `gradle wrapper`
├── plugin/
│   ├── build.gradle.kts
│   └── src/main/
│       ├── kotlin/com/example/myplugin/
│       │   ├── MyPluginNames.kt           (shared constants)
│       │   ├── MyComponentRegistrar.kt
│       │   ├── MyCommandLineProcessor.kt
│       │   └── MyIrGenerationExtension.kt
│       └── resources/META-INF/services/
│           ├── org.jetbrains.kotlin.compiler.plugin.CompilerPluginRegistrar
│           └── org.jetbrains.kotlin.compiler.plugin.CommandLineProcessor
└── sample/
    ├── build.gradle.kts
    └── src/main/kotlin/Main.kt
```

The two halves:
- **`plugin/`** is the compiler plugin. It compiles to a JAR that the Kotlin compiler loads via `-Xplugin=`.
- **`sample/`** is a normal Kotlin project that exercises the plugin. It is the easiest way to verify plugin behaviour end-to-end.

## settings.gradle.kts

```kotlin
plugins {
```

The Foojay Toolchain Resolver lets Gradle download the JDK declared by `jvmToolchain(...)` if it isn't installed locally — without it the build fails when the requested JDK is missing.

## plugin/build.gradle.kts

```kotlin
plugins {
    kotlin("jvm") version "2.3.21"  // pick the latest 2.3.x at the time you start
}

kotlin {
    jvmToolchain(21)
}

dependencies {
    compileOnly("org.jetbrains.kotlin:kotlin-compiler-embeddable:2.3.21")
}
```

`compileOnly` is critical here. When your plugin runs inside `kotlinc`, the embeddable JAR is already on the compiler's classloader; bundling it again creates duplicate-class conflicts. (For integration tests, see the [`compiler-plugin-testing`](../compiler-plugin-testing/guide.md) skill — testing uses a separate `sample/` module that loads the plugin via `-Xplugin=`.)

**Do not add `kotlin-stdlib` as `implementation`.** The Kotlin Gradle plugin pulls it in transitively as `implementation` by default — for a *normal* JVM module that's correct, but for a compiler plugin JAR it bundles stdlib classes that the compiler classloader already provides. Real plugins in `kotlin/plugins/` declare stdlib `compileOnly` (or skip it entirely if not needed at the source level) so the published artefact has a thin classpath.

**`compileOnly` does not propagate transitively.** When a downstream Gradle module depends on `:plugin`, `compileOnly` is invisible to it; this is the desired behaviour for a plugin JAR. The trap is the inverse — switching to `implementation` to make IDE resolution easier will leak `kotlin-compiler-embeddable` into every consumer's runtime classpath.

## Shared plugin ID constant

Hoist the plugin ID into a single constant so the registrar and CLI processor can't drift:

```kotlin
package com.example.myplugin

object MyPluginNames {
    const val PLUGIN_ID = "com.example.myplugin"
}
```

(Real-world precedent: `kotlin/plugins/allopen/allopen.common/src/.../AllOpenPluginNames.kt`.)

## CompilerPluginRegistrar

```kotlin
package com.example.myplugin

import org.jetbrains.kotlin.backend.common.extensions.IrGenerationExtension
import org.jetbrains.kotlin.compiler.plugin.CompilerPluginRegistrar
import org.jetbrains.kotlin.compiler.plugin.ExperimentalCompilerApi
import org.jetbrains.kotlin.config.CompilerConfiguration

@OptIn(ExperimentalCompilerApi::class)
class MyComponentRegistrar : CompilerPluginRegistrar() {
    override val pluginId: String = MyPluginNames.PLUGIN_ID
    override val supportsK2: Boolean = true

    override fun ExtensionStorage.registerExtensions(configuration: CompilerConfiguration) {
        // The IrGenerationExtension shown later in this skill takes a MessageCollector
        // constructor argument so it can emit visible warnings. Pull it from the
        // configuration here and pass it in:
        val messageCollector = configuration.get(
            CommonConfigurationKeys.MESSAGE_COLLECTOR_KEY,
            MessageCollector.NONE,
        )
        IrGenerationExtension.registerExtension(MyIrGenerationExtension(messageCollector))
        // FIR extensions are registered via FirExtensionRegistrarAdapter — see
        // the fir-extensions skills.
    }
}
```

You'll also need these imports in the registrar file:

```kotlin
import org.jetbrains.kotlin.cli.common.messages.MessageCollector
import org.jetbrains.kotlin.config.CommonConfigurationKeys
```

Three abstract members must be overridden:

| Member | Purpose |
|---|---|
| `pluginId: String` | Plugin identifier. Must match the `pluginId` of the corresponding `CommandLineProcessor`. Used by `-Xcompiler-plugin-order` to control plugin ordering. **Required since Kotlin 2.3** — older guides may omit it. ⚠️ The inverse holds for older targets: `pluginId` does **not exist** on `CompilerPluginRegistrar` in Kotlin 2.2.20 and earlier. A plugin compiled against `kotlin-compiler-embeddable:2.2.20` that overrides `pluginId` will fail with "'pluginId' overrides nothing"; a plugin built without it will fail to load on 2.3+ with the inverse error. Multi-version plugins must split their registrar source per Kotlin version. |
| `supportsK2: Boolean` | Set to `true` for new plugins. K1 (the legacy frontend) is being removed. |
| `registerExtensions(...)` | Where you wire up the actual extensions. The `ExtensionStorage` receiver provides `registerExtension` as an extension function on `ProjectExtensionDescriptor<T>`; `IrGenerationExtension`'s companion is itself such a descriptor, so `IrGenerationExtension.registerExtension(...)` works directly. |

`ExtensionStorage` is the registrar's helper type that collects registered extensions and disposables — you don't construct it; the compiler passes it in as receiver.

## CommandLineProcessor

```kotlin
package com.example.myplugin

import org.jetbrains.kotlin.compiler.plugin.CliOption
import org.jetbrains.kotlin.compiler.plugin.CommandLineProcessor
import org.jetbrains.kotlin.compiler.plugin.ExperimentalCompilerApi

@OptIn(ExperimentalCompilerApi::class)
class MyCommandLineProcessor : CommandLineProcessor {
    override val pluginId: String = MyPluginNames.PLUGIN_ID
    override val pluginOptions: Collection<CliOption> = emptyList()
}
```

Even when your plugin takes no options, you must still ship a `CommandLineProcessor` — it is what allows users to pass `-P plugin:com.example.myplugin:key=value` arguments. The registrar wires extensions; the processor parses options. The compiler discovers them independently via two separate service files.

To accept options, declare them via `CliOption` and parse them in `processOption`:

```kotlin
package com.example.myplugin

import org.jetbrains.kotlin.compiler.plugin.AbstractCliOption
import org.jetbrains.kotlin.compiler.plugin.CliOption
import org.jetbrains.kotlin.compiler.plugin.CliOptionProcessingException
import org.jetbrains.kotlin.compiler.plugin.CommandLineProcessor
import org.jetbrains.kotlin.compiler.plugin.ExperimentalCompilerApi
import org.jetbrains.kotlin.config.CompilerConfiguration
import org.jetbrains.kotlin.config.CompilerConfigurationKey

val ENABLED_KEY = CompilerConfigurationKey<Boolean>("enabled")

@OptIn(ExperimentalCompilerApi::class)
class MyCommandLineProcessor : CommandLineProcessor {
    private val enabledOption = CliOption(
        optionName = "enabled",
        valueDescription = "<true|false>",
        description = "Whether the plugin should run",
        required = false,
        allowMultipleOccurrences = false,
    )

    override val pluginId: String = MyPluginNames.PLUGIN_ID
    override val pluginOptions: Collection<CliOption> = listOf(enabledOption)

    override fun processOption(
        option: AbstractCliOption,
        value: String,
        configuration: CompilerConfiguration,
    ) {
        when (option.optionName) {
            enabledOption.optionName -> configuration.put(ENABLED_KEY, value.toBoolean())
            else -> throw CliOptionProcessingException("Unknown option: ${option.optionName}")
        }
    }
}
```

The registrar reads the option back via `configuration[ENABLED_KEY]`. The `else` branch is required: without it, an unrecognised `-P plugin:...` arg silently falls through.

## IrGenerationExtension (with visible side effect)

```kotlin
package com.example.myplugin

import org.jetbrains.kotlin.backend.common.extensions.IrGenerationExtension
import org.jetbrains.kotlin.backend.common.extensions.IrPluginContext
import org.jetbrains.kotlin.cli.common.messages.CompilerMessageSeverity
import org.jetbrains.kotlin.cli.common.messages.MessageCollector
import org.jetbrains.kotlin.config.CommonConfigurationKeys
import org.jetbrains.kotlin.config.CompilerConfiguration
import org.jetbrains.kotlin.ir.declarations.IrModuleFragment

class MyIrGenerationExtension(
    private val messageCollector: MessageCollector,
) : IrGenerationExtension {
    override fun generate(moduleFragment: IrModuleFragment, pluginContext: IrPluginContext) {
        messageCollector.report(
            CompilerMessageSeverity.WARNING,
            "MyPlugin: scanned module '${moduleFragment.name}' with ${moduleFragment.files.size} file(s)",
        )
    }
}
```

The matching `registrar.registerExtensions` body that wires this up was already shown in the **CompilerPluginRegistrar** section above — it pulls `MESSAGE_COLLECTOR_KEY` from the configuration and passes it to `MyIrGenerationExtension(messageCollector)`.

Why this matters: a stub `generate(...)` with an empty body is indistinguishable from "plugin never loaded". A `MessageCollector.report(WARNING, ...)` call surfaces in Gradle's console (`w: ...` line) so a successful build with no plugin output means the plugin silently failed to register. With this in place you have a positive end-to-end signal.

For frontend (FIR) hooks see the `fir-*` skills.

## META-INF/services registration

The Kotlin compiler discovers plugins via Java's ServiceLoader. Two text files are required:

**`plugin/src/main/resources/META-INF/services/org.jetbrains.kotlin.compiler.plugin.CompilerPluginRegistrar`**

```
com.example.myplugin.MyComponentRegistrar
```

**`plugin/src/main/resources/META-INF/services/org.jetbrains.kotlin.compiler.plugin.CommandLineProcessor`**

```
com.example.myplugin.MyCommandLineProcessor
```

One FQN per line; multiple lines are allowed if your plugin ships several registrars. Forgetting these silently disables the plugin — the build succeeds, the JAR is on the classpath, but no service is discovered and no `MessageCollector.report` line appears.

Verify:

```bash
unzip -l plugin/build/libs/plugin.jar | grep META-INF/services
```

(The JAR filename is `<subproject-name>.jar` — `plugin.jar` here because the subproject is `plugin`.)

## sample/build.gradle.kts (consuming the plugin)

For an experimentation harness, depend on the plugin JAR via a custom configuration and inject `-Xplugin=` directly:

```kotlin
import org.jetbrains.kotlin.gradle.tasks.KotlinCompile

plugins {
    kotlin("jvm") version "2.3.21"
    application
}

kotlin {
    jvmToolchain(21)
}

application {
    mainClass.set("MainKt")
}

// Treat the plugin JAR as a build dependency, then pass its path to kotlinc via -Xplugin.
val compilerPlugin: Configuration by configurations.creating

dependencies {
    compilerPlugin(project(":plugin"))
}

tasks.withType<KotlinCompile>().configureEach {
    inputs.files(compilerPlugin)
    compilerOptions.freeCompilerArgs.add(
        compilerPlugin.elements.map { files ->
            "-Xplugin=${files.first().asFile.absolutePath}"
        }
    )
}
```

The `compilerPlugin.elements.map { ... }` returns a `Provider<String>` so the plugin JAR path is resolved lazily at execution time, not at configuration time. `inputs.files(compilerPlugin)` declares the JAR as a task input so changes invalidate the cache.

Note: `-Xplugin=` accepts a comma-separated list and is the legacy form. Kotlin 2.x also supports `-Xcompiler-plugin=<path1>,<path2>[=<optionName>=<value>,<optionName>=<value>]` (paths first, then options after `=`). And `-P plugin:<id>:<key>=<value>` is the legacy way to pass options. For an experimentation harness `-Xplugin=` is fine; the proper Gradle plugin (see [`gradle-plugin-integration`](../gradle-plugin-integration/guide.md)) uses the newer `-Xcompiler-plugin` form automatically.

For a plugin you intend to ship to other users, replace this manual wiring with a proper Gradle plugin extending `KotlinCompilerPluginSupportPlugin` — see the [`gradle-plugin-integration`](../gradle-plugin-integration/guide.md) skill.

## End-to-end verification

From a host machine that already has Gradle installed:

```bash
# One-time: generate the wrapper so subsequent runs are reproducible.
# Use the full three-component version — `9.5` alone fails distribution-URL lookup.
gradle wrapper --gradle-version 9.5.0

# Then for every build:
./gradlew :sample:run
```

(If you don't have a host Gradle, install via `brew install gradle`, SDKMAN's `sdk install gradle`, or download from gradle.org.)

Expected behaviour, in order:
1. `:plugin:compileKotlin` — plugin sources compile
2. `:plugin:jar` — plugin JAR is built
3. `:sample:compileKotlin` — sample compiles, with the plugin loaded; the `MessageCollector.report` from `generate(...)` appears as a `w:` warning line in Gradle's console
4. `:sample:run` — the sample's `main()` runs, printing `hello from sample`

If you see `:sample:compileKotlin` succeed without the `w: MyPlugin: scanned module ...` line, the plugin failed to register — see the **Common gotchas** section.

## Inspecting the result

Two complementary inspection tools:

```bash
# Show the bytecode of any class the plugin touched
javap -p -c sample/build/classes/kotlin/main/MainKt.class
```

To dump IR or surface compiler-plugin debug output, add the right `freeCompilerArgs` flag in `sample/build.gradle.kts` (e.g. `compilerOptions.freeCompilerArgs.add("-Xverbose-phases=...")` for phase tracing). `-Xprint-ir` is Native-only and not useful on a JVM `sample`. See [`compiler-plugin-debugging`](../compiler-plugin-debugging/guide.md) for the full set of flags and how to dump FIR / IR via the test framework instead.

## Common gotchas

### `Class 'MyComponentRegistrar' is not abstract and does not implement abstract member 'public abstract val pluginId: String defined in ...'`

You're missing `override val pluginId: String = ...` on either `CompilerPluginRegistrar` or `CommandLineProcessor`. Required since Kotlin 2.3 (commit "[Plugins] Require a unique pluginId for all compiler plugins", on `2.3.0` branch and later).

### `IllegalArgumentException: 25.0.2` from `JavaVersion.parse`

The Gradle launcher is running on Java 25, but the bundled Kotlin compiler in your Gradle distribution can't parse that version string. See the `gradle.properties` section above — pin `org.gradle.java.home` to JDK 21. Tracked as a Kotlin 2.3.x BTAPI issue (still present in 2.3.21); likely resolved in 2.4.x.

### Plugin compiles, build succeeds, but no `w:` line from `generate(...)`

Most common cause: `META-INF/services` file missing, mis-named (typos in the FQN matter — the filename **is** the interface FQN), or the FQN inside is wrong. Verify with the `unzip` command above; check both the file path and the contents.

ServiceLoader file format requirements:
- UTF-8, **no BOM** (some IDE auto-creators add a BOM that breaks discovery)
- One FQN per line, no leading/trailing whitespace
- File extension: none — the filename `org.jetbrains.kotlin.compiler.plugin.CompilerPluginRegistrar` has no `.txt` suffix

Other causes:
- Plugin JAR not on the consumer's `-Xplugin=` arg. Check Gradle's `--info` output for the `Kotlin compiler args:` line.
- **Daemon caching an older plugin JAR.** After modifying plugin source, the Kotlin compile daemon may keep the previous classloader. Run `./gradlew --stop` and rebuild, or set `kotlin.compiler.execution.strategy=in-process` in `gradle.properties` while iterating.
- `compileOnly` was changed to `implementation`, causing duplicate-class conflicts that prevent loading.
- Multiple registrars on the classpath (your `:plugin` plus a transitive dependency that ships the same service file): the registrar then runs twice and your extensions register twice. Audit with `unzip -p .../plugin.jar META-INF/services/org.jetbrains.kotlin.compiler.plugin.CompilerPluginRegistrar`.

### Plugin runs at compile time but IntelliJ shows no effect

`-Xplugin=` only affects Gradle compilation, not IntelliJ's in-IDE Kotlin analyzer. The IDE has its own plugin discovery path: it uses the `KotlinCompilerPluginSupportPlugin`-published Gradle plugin, *not* the raw JAR. This is by design — the IDE analyzer runs separately from compilation. To get in-IDE behaviour, package your plugin via `KotlinCompilerPluginSupportPlugin` (see [`gradle-plugin-integration`](../gradle-plugin-integration/guide.md)) and ensure the IntelliJ Kotlin plugin can discover it through the Gradle import.

### `@OptIn(ExperimentalCompilerApi::class)` warnings everywhere

The compiler plugin API is intentionally `@ExperimentalCompilerApi` — JetBrains reserves the right to break it across minor versions. You can use file-level opt-in for cleaner code:

```kotlin
@file:OptIn(org.jetbrains.kotlin.compiler.plugin.ExperimentalCompilerApi::class)
package com.example.myplugin
// ...
```

Some IR APIs additionally require `@OptIn(UnsafeDuringIrConstructionAPI::class)` — see [`ir-plugincontext-usage`](../ir-plugincontext-usage/guide.md).

### Version mismatch between plugin and consumer

The `kotlin-compiler-embeddable` version used by the plugin must match the Kotlin version that compiles the consumer. If the consumer compiles with Kotlin 2.3.21, the plugin must depend on `kotlin-compiler-embeddable:2.3.21`. Mismatches cause `NoSuchMethodError` or `LinkageError` at the consumer's compile time — see [`multi-version-kotlin-support`](../multi-version-kotlin-support/guide.md) for strategies if you need to support multiple Kotlin versions.

### Wrong artifact

`org.jetbrains.kotlin:kotlin-compiler` is **not** the right dependency — it pulls in unrelocated `com.intellij.*` and `org.jetbrains.org.objectweb.asm` classes that clash with Gradle's own classpath and with anything else that uses ASM. Always use `kotlin-compiler-embeddable` (where these classes are shaded under `org.jetbrains.kotlin.com.intellij.*`).

### Registrar with constructor arguments fails to load

`ServiceLoader` instantiates registrars via the no-argument constructor. If you give your registrar a primary constructor with parameters (often when sharing one class across multiple plugin entry points), add an explicit no-arg constructor that delegates:

```kotlin
class MyComponentRegistrar(private val flags: Set<Flag>) : CompilerPluginRegistrar() {
    @Suppress("unused")
    constructor() : this(emptySet())
    // ...
}
```

(Pattern from `kotlin/plugins/power-assert/.../PowerAssertCompilerPluginRegistrar.kt`.)

## Production layout (when you outgrow this skeleton)

This skill ships a single `plugin/` module to keep the bootstrap minimal. Production-grade plugins under `kotlin/plugins/` (allopen, noarg, kotlinx-serialization, parcelize, power-assert) split sources across several modules:

| Module | Holds |
|---|---|
| `<plugin>.common` | `PluginNames`, `CliOption` declarations, `CompilerConfigurationKey`s — shared by every entry point |
| `<plugin>.cli` | `CompilerPluginRegistrar` + `CommandLineProcessor` + `META-INF/services` |
| `<plugin>.k1` | (legacy) K1 frontend extensions |
| `<plugin>.k2` | K2/FIR frontend extensions (`FirExtensionRegistrar` + extensions) |
| `<plugin>.backend` | `IrGenerationExtension` and IR transforms |
| `<plugin>.embeddable` | a shaded JAR for consumers using `kotlin-compiler-embeddable` |

The split lets each module depend on the smallest slice of compiler API it needs, makes K1 removal a single-module deletion, and isolates the embeddable shading. For the bootstrap, stay flat; refactor when you start adding FIR.
