# FIR (K2 Frontend) Extension System

This skill explains how the K2 frontend extension system is wired and lists the available extension points. Each extension point has its own skill (`fir-additional-checkers-extension`, `fir-declaration-generation-extension`, etc.) that goes deep on usage. Read this skill first to know which one you need.

## Where FIR fits in the compilation pipeline

```
Kotlin source ──► PSI ──► FIR (K2 frontend) ──► IR ──► bytecode
                          ▲                     ▲
                          │                     │
                          fir-* extensions      ir-* extensions
```

FIR is the **frontend**: parsing, name resolution, type-checking, overload resolution, and frontend-level diagnostics happen here. By the time IR is built, FIR has already classified every reference, resolved every call, and applied every checker.

If you need to *understand or constrain source-level semantics* (custom diagnostics, synthetic members visible to user code, modified visibility), you write a FIR extension. If you need to *transform compiled output* (call rewriting, body modification, generated bytecode), you write an IR extension. Many plugins have both.

## How a FIR extension hooks into the bootstrap scaffold

The compiler discovers your plugin via `CompilerPluginRegistrar` (see `compiler-plugin-bootstrap`). To run any FIR code, you register a `FirExtensionRegistrar` through `FirExtensionRegistrarAdapter`:

```kotlin
@OptIn(ExperimentalCompilerApi::class)
class MyComponentRegistrar : CompilerPluginRegistrar() {
    override val pluginId: String = MyPluginNames.PLUGIN_ID
    override val supportsK2: Boolean = true

    override fun ExtensionStorage.registerExtensions(configuration: CompilerConfiguration) {
        FirExtensionRegistrarAdapter.registerExtension(MyFirExtensionRegistrar())
        // IR extensions register alongside, separately:
        IrGenerationExtension.registerExtension(MyIrGenerationExtension())
    }
}
```

`FirExtensionRegistrarAdapter` is the bridge between the plugin-API world (where `ExtensionStorage` lives) and the FIR world (where `FirExtensionRegistrar` lives). You don't subclass it — you subclass `FirExtensionRegistrar` and pass an instance to the adapter's static `registerExtension`.

## Writing a FirExtensionRegistrar

```kotlin
class MyFirExtensionRegistrar : FirExtensionRegistrar() {
    override fun ExtensionRegistrarContext.configurePlugin() {
        +::MyDeclarationGenerator              // (FirSession) -> FirDeclarationGenerationExtension
        +::MyChecker                           // (FirSession) -> FirAdditionalCheckersExtension
        +::MyStatusTransformer                 // (FirSession) -> FirStatusTransformerExtension
    }
}
```

The `+` operator inside `configurePlugin()` is overloaded for every supported extension point. You can pass:

- A constructor reference: `+::MyDeclarationGenerator` where the constructor takes a `FirSession`
- An explicit lambda: `+{ session: FirSession -> MyDeclarationGenerator(session, customArg) }`
- A `Factory` instance directly: `+MyDeclarationGenerator.Factory { session -> ... }`

Each extension class declares a nested `Factory` interface (e.g. `FirDeclarationGenerationExtension.Factory`). The registrar wires *factories*, not instances — the compiler creates one instance per `FirSession`.

(See `kotlin/compiler/fir/entrypoint/src/org/jetbrains/kotlin/fir/extensions/FirExtensionRegistrar.kt` for the full DSL.)

## FirSession lifecycle

A `FirSession` is the per-module compilation context that holds the symbol table, type system, diagnostics storage, and your registered extensions. Two session kinds exist:

| Kind | When | What plugins can register |
|---|---|---|
| `Source` | for the module being compiled | All extension points |
| `Library` | for read-only dependencies | Only `FirTypeAttributeExtension` and `FirFunctionTypeKindExtension` |

Most plugins only care about Source sessions. Your extension's constructor is called once per session, so don't put global state in the constructor — use the session's symbol provider and scopes instead.

In IDE mode, sessions are recreated on file changes; the registrar survives. The `FirExtensionRegistrar` uses a synchronised `lazy` to ensure `configurePlugin()` runs exactly once even across recreations.

Listed in approximate frequency of real-world use (counted across `kotlin/plugins/*/`). Each row points to its dedicated skill (planned).

| `FirAdditionalCheckersExtension` | Add custom diagnostics (errors / warnings) on declarations, expressions, types | `fir-additional-checkers-extension` |
| `FirSupertypeGenerationExtension` | Inject or rewrite supertypes of existing classes | `fir-supertype-generation-extension` |
| `FirStatusTransformerExtension` | Modify modifiers (visibility, openness, modality) on existing declarations | `fir-status-transformer-extension` |
| `FirScriptConfiguratorExtension` | Configure source-level script compilation (`.kts` dialects) | `fir-scripting-extensions` |
| `FirScriptResolutionConfigurationExtension` | Inject default imports into script bodies | `fir-scripting-extensions` |
| `FirExpressionResolutionExtension` | Customise how specific expressions are resolved | `fir-expression-resolution-extension` |
| `FirReplSnippetConfiguratorExtension` | Configure REPL snippet compilation | `fir-repl-snippet-extensions` |
| `FirReplSnippetResolveExtension` | Drive name-resolution and cross-snippet visibility during REPL snippet compilation (added in the 2.1 cycle) | `fir-repl-snippet-extensions` |
| `FirSamConversionTransformerExtension` | Refine SAM (single-abstract-method) conversion — e.g. promote first parameter to receiver | `fir-sam-conversion-transformer-extension` |

| `FirAssignExpressionAltererExtension` | Hook into the desugaring of `=` on properties (`x = v` → `x.assign(v)`) | `fir-assign-expression-alterer-extension` |
| `FirTypeAttributeExtension` | Attach plugin-defined attributes to types via annotations (`@Positive Int`); allowed in library sessions | `fir-type-attribute-extension` |
| `Fir2IrScriptConfiguratorExtension` | Bridge script config from FIR to IR | `fir-scripting-extensions` |

The authoritative list lives at `FirExtensionRegistrar.AVAILABLE_EXTENSIONS` (line 23 of `compiler/fir/entrypoint/src/org/jetbrains/kotlin/fir/extensions/FirExtensionRegistrar.kt` at v2.3.21); **18 entries total** (the `FirReplSnippetResolveExtension::class` entry was added in the 2.1 cycle — not present at v2.0.21, present at v2.1.20). Extensions not in that list cannot be registered through the registrar DSL.

### Note on `FirMetadataSerializerPlugin`

This extension point is publicly listed in `AVAILABLE_EXTENSIONS` but its KDoc explicitly tells you not to use it:

> *This extension point is temporary and should not be used. It will be removed soon: [KT-64695](https://youtrack.jetbrains.com/issue/KT-64695). DON'T USE IT.*
> — `FirMetadataSerializerPlugin.kt` at v2.3.21, lines 22-25.

It is gated behind `@FirExtensionApiInternals` (the same opt-in as `FirFunctionCallRefinementExtension`) and exists solely to support legacy kotlinx-serialization metadata patches inside the Kotlin monorepo. New plugins should not depend on it; if you need to influence what reaches consumers' classpath, prefer `metadataDeclarationRegistrar.registerFunctionAsMetadataVisible(...)` and `metadataDeclarationRegistrar.addMetadataVisibleAnnotationsToElement(...)` from an `IrGenerationExtension` (see `ir-synthetic-class-generation` and `ir-plugincontext-usage`).

## How to choose

Match the **what** to the extension point:

| Goal | Extension |
|---|---|
| "Reject code that does X" — show a red squiggle | `FirAdditionalCheckersExtension` |
| "Generate a `companion object` / `toString()` / serializer" — usable from source **within the same module** (pair with an `IrGenerationExtension` to fill the body); for a member visible only to *downstream modules* (the kotlinx-serialization `write$Self` idiom), use IR-side generation + `metadataDeclarationRegistrar.registerFunctionAsMetadataVisible(...)` instead | `FirDeclarationGenerationExtension` |
| "Inject a marker / serializer interface as a supertype on the *companion* of every annotated class" (the supertype goes on the companion, not on the class itself — kotlinx-serialization is the canonical user) | `FirSupertypeGenerationExtension` |
| "Make a `class` annotated `@Open` and its members `open` so consumers can subclass / override" — note: `data class`, `enum class`, `object` are forbidden from being `open` regardless of plugin | `FirStatusTransformerExtension` |
| "Cache resolved metadata once per session and share across my extensions" | `FirExtensionSessionComponent` |
| "Inject an implicit extension receiver inside `myDsl { ... }` so `foo()` resolves as `Dsl.foo()`" (return-type refinement is a different extension; see the bottom row) | `FirExpressionResolutionExtension` |
| "Customise property assignment to call a custom setter" (`x = v` → `x.assign(v)`) | `FirAssignExpressionAltererExtension` |
| "Promote the first SAM-method parameter to a receiver so lambdas can use `this`" | `FirSamConversionTransformerExtension` |
| "Distinguish `@Positive Int` from `Int` in type checking" (FIR-only — pair with checkers; no IR-side machinery needed) | `FirTypeAttributeExtension` |
| "Make `@Composable () -> Unit` a different type from `() -> Unit`" (requires a paired `IrGenerationExtension` lowering — synthetic kinds don't survive to bytecode by themselves) | `FirFunctionTypeKindExtension` |
| "Refine a call's return type at the call site by injecting a local schema class" (data-frame style) — refinement works at the FIR level, but successfully reaching bytecode requires a substantial paired IR rewriter; the extension is `@FirExtensionApiInternals` and the upstream tests run only `RUN_PIPELINE_TILL: FRONTEND` | `FirFunctionCallRefinementExtension` (advanced, unstable, IR-incomplete) |

If the goal is to *replace a function call's bytecode* or *modify a function's body*, that's an IR transformation — use `IrGenerationExtension`, not a FIR extension.

## The predicate system (preview)

Most FIR plugins target declarations matching some annotation pattern (e.g. "every `@Serializable` class"). FIR provides a declarative `DeclarationPredicate` DSL — `annotated(...)`, `parentAnnotated(...)`, `ancestorAnnotated(...)`, `metaAnnotated(...)`, etc. — registered by overriding `FirExtension.registerPredicates()` on each extension. The pipeline then collects matching declarations through `FirPredicateBasedProvider`, which extensions query at lookup time via `session.predicateBasedProvider`.

The predicate system has its own skill (`fir-predicate-system`). Up-front registration lets the FIR pipeline collect annotated declarations and answer matches/lookups uniformly, instead of every extension walking annotations on every declaration.

## Generated diagnostics

When your `FirAdditionalCheckersExtension` reports diagnostics declared via `KtDiagnosticFactory*`, those factories must be registered with the FIR session. The `FirExtensionRegistrar` exposes `registerDiagnosticContainers(...)` for this:

```kotlin
override fun ExtensionRegistrarContext.configurePlugin() {
    +::MyChecker
    registerDiagnosticContainers(MyDiagnostics)
}
```

Where `MyDiagnostics` is your `KtDiagnosticsContainer` subclass. Forgetting this causes "diagnostic factory was not registered" errors at compile time of the consumer. Details in `fir-additional-checkers-extension`.

## State sharing via FirExtensionSessionComponent

The dominant idiom for sharing computed state across extensions in the same session is `FirExtensionSessionComponent`. Every non-trivial plugin uses it (compose, kotlinx-serialization, lombok, parcelize, atomicfu).

```kotlin
class MyMetadataService(session: FirSession) : FirExtensionSessionComponent(session) {
    private val cache = session.firCachesFactory.createCache<ClassId, MyMetadata> { /* compute */ }
    fun metadataOf(classId: ClassId): MyMetadata = cache.getValue(classId)

    companion object {
        fun getFactory(): Factory = Factory(::MyMetadataService)
    }
}

val FirSession.myMetadataService: MyMetadataService by FirSession.sessionComponentAccessor()
```

Register it like any other extension:

```kotlin
override fun ExtensionRegistrarContext.configurePlugin() {
    +::MyMetadataService
    +::MyDeclarationGenerator        // can read session.myMetadataService
    +::MyChecker                     // can also read it
}
```

The `by FirSession.sessionComponentAccessor()` pattern at file top level is canonical — it gives you a typed extension property on `FirSession` that any other extension can read. See `kotlin/plugins/kotlinx-serialization/.../services/` and `lombok/.../LombokService.kt` for production patterns.

## Common gotchas

### Extension factory constructor signature

Every FIR extension class has a constructor taking exactly one `FirSession`:

```kotlin
class MyDeclarationGenerator(session: FirSession) : FirDeclarationGenerationExtension(session) {
    // ...
}
```

The base class `FirDeclarationGenerationExtension(session)` (and every other extension base) takes the session as its primary constructor argument. Forgetting to pass it produces an unhelpful error.

### `+` operator does nothing if you don't call `configurePlugin()`

`configurePlugin()` is `protected abstract`, called by the compiler via the registrar's lazy initialisation. Don't call it yourself. Just override it; the framework calls it once.

### Library sessions silently drop most extensions

If your extension behaviour seems to apply only to the current module and not its dependencies, that's expected — only `FirTypeAttributeExtension` and `FirFunctionTypeKindExtension` run in library sessions. Source-only extensions are *not* re-applied to dependency declarations; the compiler trusts that those declarations were already processed when their owning module was compiled.

### `@FirExtensionApiInternals` extensions

`FirFunctionCallRefinementExtension` and `FirMetadataSerializerPlugin` are gated behind `@FirExtensionApiInternals` and may break across patch versions without warning. Avoid unless you're maintaining a JetBrains-internal plugin or have a problem the public extensions can't solve.

### One Factory per FirSession, not per file

Each session gets one extension instance, but a session can compile many files. Don't store per-file state in the extension — use FIR's symbol provider to look things up at the point of use.

### Predicates live on the `FirExtension`, not the registrar

`registerPredicates()` is overridden on each extension class (`FirExtension.registerPredicates()`), not inside `configurePlugin()`. Forgetting to override it on the extension silently disables every annotation-based lookup that extension needs.

### `Fir2IrExtensions` is a separate hierarchy

Don't try to register Fir2Ir behaviour through `FirExtensionRegistrar`. `Fir2IrExtensions` (in `compiler/fir/fir2ir/`) is a different interface plumbed via the Fir2Ir pipeline — typically configured through scripting/REPL extensions or `IrGenerationExtension`, not via the FIR registrar.

### Symbol resolution timing

Don't call `session.symbolProvider.getClassLikeSymbolByClassId(...)` from your extension's constructor — other components may not be wired yet. Defer to the phase callbacks each extension exposes (`generateClassLikeDeclaration`, `getCallableNamesForClass`, `check(declaration)` — the actual checker signature uses context parameters in Kotlin 2.3.x, see `fir-additional-checkers-extension`).

### `supportsK2 = true` is mandatory

If your `CompilerPluginRegistrar.supportsK2` is `false` (or omitted on legacy `ComponentRegistrar`), `FirExtensionRegistrarAdapter.registerExtension` is silently never reached — your FIR extensions don't run, even though the build succeeds.

### IDE-mode session recreation

Don't store session-keyed state on the *registrar* — the registrar outlives sessions in IDE mode, so any `FirSession` reference captured there is leaked when sessions are recreated. Per-session state belongs on `FirExtensionSessionComponent`.

### `registerDiagnosticContainers` is gated to Source sessions

The call is silently a no-op for Library sessions (`FirExtensionRegistrar.kt:341-343` at v2.3.21). This is the correct behaviour — diagnostics on already-compiled library code wouldn't make sense — but readers may wonder why their library-applied checker doesn't report.
